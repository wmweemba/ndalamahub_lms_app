# Auth (server-side sessions, Phase 25)

Moved verbatim from CLAUDE.md on 2026-10-21. Loads only when Claude works with matching files. Full prior file: `docs/history/CLAUDE-2026-10-21.md`.

**Current (Phase 25, complete)**: server-side sessions — `express-session` + `connect-mongo` (sessions stored in the same Mongo the app already uses, `sessions` collection), replacing the old JWT/localStorage implementation entirely. Cookie `ndalamahub.sid`: `httpOnly`, `secure` in production, `sameSite: 'lax'`, rolling ~24h idle expiry, plus a 7-day absolute cap enforced in `middleware/auth.js` (`session.createdAt`, independent of the cookie's own rolling expiry). `server/middleware/session.js` builds the store off `mongoose.connection`'s own client (via a `'connected'`-event-based `clientPromise`, not `Connection.asPromise()` — that resolves immediately against an unset `$initialConnection` when called before any `connect()` attempt, which is true of both `server.js`'s fire-and-forget `connectDB()` call and every API test file).

`middleware/auth.js`'s `loadUser` (global, mounted in `app.js` right after the session middleware, before every route) loads the session's user fresh from Mongo on **every** request and attaches the same `{id, username, role, company}` shape routes have always read — if the session resolves to no user or an inactive one, it destroys the session and 401s immediately, which is what makes deactivation take effect on a deactivated user's *very next* request rather than waiting out a token's remaining lifetime (closes the 7-day-stale-JWT hole flagged since Phase 06). `requireAuth` is the per-route guard that replaced every `authenticateToken` call site (just checks `req.user` is set — the actual loading already happened globally). `middleware/originCheck.js` is the CSRF posture: rejects unsafe-method (POST/PUT/PATCH/DELETE) requests whose `Origin` header is present and doesn't match `CORS_ORIGIN`/`APP_URL` — a same-site SPA doesn't need a token dance, `sameSite: 'lax'` plus this check is the whole story (the Phase 22 public-intake routes are exempt; they're never session-authenticated and pin their own per-lender CORS). `routes/auth.js`: `/login` regenerates the session (fixation defence) and returns the safe user subset (`firstName`/`lastName`/`email` included, unlike the old hand-built JWT payload); `/logout` destroys the session; `/refresh` no longer exists (sessions have no refresh concept); `SESSION_SECRET` replaces `JWT_SECRET` in the boot-time fail-fast list and `.env.example`. `jsonwebtoken` is gone from `package.json` — nothing in the codebase references it.

Client: `utils/api.js` sends the cookie via `withCredentials: true` (no more `Authorization` header, no request interceptor); a 401 response clears the cached user and hard-redirects to `/login` (skipped for the boot-time hydration probe itself, via a `skipAuthRedirect` axios config flag, since `ProtectedRoute`'s own redirect already handles that case). The current user lives in an in-memory cache (`utils/authState.js` — a dependency-free leaf module, deliberately *not* merged into `roleUtils.js` itself: `api.js` needs to import its `clearCurrentUser()` for the 401 handler, and importing the api-dependent `roleUtils.js` would cycle back; the global Vitest setup file also needs to reset this state without ever pulling in `api.js`, or a test file's own `vi.mock('@/utils/api', ...)` gets silently defeated for that whole file — hit and fixed while writing the Phase 25 client tests). `roleUtils.getCurrentUser()` keeps its exact synchronous signature for the dozens of existing call sites; `roleUtils.ensureHydrated()` is the one async entry point that fills the cache from `GET /auth/me` on app boot (a fresh tab or a page refresh), called once by `ProtectedRoute`, which holds a loading state until it resolves rather than flashing an authenticated user through `/login` on every refresh. A Vite dev proxy (`vite.config.js`, `/api` → `http://localhost:5000`) makes the cookie first-party in dev; `VITE_API_URL` is unset by default now and only needed for a non-proxied setup. Staff TOTP MFA remains post-launch (unchanged decision). See `docs/25-auth-sessions-migration.md` and `changelog.md`'s 2026-07-23 Phase 25 entries (Session A: server: Session B: client) for the full per-step account, including the manual live-verification pass against the dev Atlas DB (login/refresh/logout/deactivation-lockout across roles, all confirmed).
