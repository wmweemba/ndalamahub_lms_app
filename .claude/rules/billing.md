# Billing & subscriptions

Moved verbatim from CLAUDE.md on 2026-10-21. Loads only when Claude works with matching files. Full prior file: `docs/history/CLAUDE-2026-10-21.md`.

**Billing/subscription gating** (built Phase 10, `server/middleware/subscription.js`) composes with this layer rather than replacing it: `companyLenderId` is how an employer/borrower's *paying lender* is resolved for gating purposes, exactly as it's used here for read/write scoping. Tenancy answers "which documents"; the subscription gate answers "is this tenant's business access currently on at all" — the lifecycle is in `server/jobs/expireSubscriptions.js`.

**Manual billing and the billing audit log (subscription-billing build, 2026-10-20):** no payment processor; all money is recorded by hand. `server/utils/subscriptionBilling.js` owns the maths: `addMonthsClamped` clamps to month-end (31 Jan + 1 month = 28/29 Feb, never 3 Mar); `computePeriodExtension` applies D1, `base = max(today, currentPeriodEnd, trialEndsAt if status === 'trialing')` then adds `periodMonths`, or uses `customPeriodEnd` when given, which must be in the future and after the current access date; `applyPayment` sets `status = 'active'`, `currentPeriodEnd`, clears `suspendedAt`, sets `plan` if given, and never touches `trialEndsAt` or `notes`. `POST /api/subscriptions/:companyId/payments` (platform_admin) writes a `SubscriptionPayment` row (currency `ZMW` by default; method `mobile_money | bank_transfer | cash | other`; amount > 0; `periodMonths` an integer 1–36 xor `customPeriodEnd`). A non-empty `reference` already used by that lender returns 409; a non-string reference returns 400. The company update is a conditional atomic update, so a concurrent change returns 409 instead of being overwritten. There are no Mongo transactions: the payment row is deleted if the company save fails, and a committed payment is never rolled back. `GET /api/subscriptions/:companyId/payments` returns the ledger. `PUT /api/subscriptions/:companyId` keeps its validation and is the manual escape hatch for suspensions, cancellations and corrections (UI label **Adjust**). **Billing audit log:** every subscription mutation writes one `BillingAuditLog` row through `server/utils/billingAudit.js` (`logBillingChange`, which never throws): `subscription.adjusted`, `subscription.payment_recorded` (linked to the ledger by `meta.paymentId`), or `subscription.status_changed` from the daily job (`source: 'system'`, `meta.kind`). Each row stores `before`/`after` snapshots of `status, plan, trialEndsAt, currentPeriodEnd, suspendedAt, notes` plus `changedFields`, and the acting user. The row is written only after a successful save, and an audit failure is logged to the console and never fails or rolls back the billing change. The log is append-only: the model rejects update, delete, replace and re-save, and there are no update or delete routes. Reminder stamps (`reminderSentFor`) are not logged. Read it with `GET /api/subscriptions/:companyId/audit` (platform_admin only), or in the UI at Settings → Billing → View history → Changes. The ledger is the financial record; the audit log is the change record. **Banner visibility (D11, rules in `roleUtils.js`):** `past_due`/`read_only` warnings go to `lender_admin` and `lender_officer`; trial-ending and renewal-soon notices (7 days out) go to `lender_admin` only. Employer-side roles and borrowers see **no** billing banner; their 402/locked handling (`AccountLockedPage`) is unchanged. `GET /api/subscriptions/status` returns `effectiveStatus`, `locked`, `readOnly` and the lender name to every role, but `status`, `plan`, `trialEndsAt` and `currentPeriodEnd` to lender staff only. The Billing table has one **Access until** column (one date, a Trial/Paid caption, and an expiry badge from 14 days out); no separate trial-end date is shown.

## Daily subscription job (from §3)

- **Scheduled jobs**: `server/jobs/scheduler.js` runs four daily cron jobs via `node-cron` (Africa/Lusaka), started from `server/server.js` unless `NODE_ENV=test` or `ENABLE_CRON=false`: `markOverdueInstallments()` (`server/jobs/markOverdueInstallments.js`, built Phase 07) at 01:00, `rolloverLoans()` (`server/jobs/rolloverLoans.js`, built Phase 20 — capitalizes the outstanding balance on rollover-enabled products once a loan is past due date + the product's `graceDays`; idempotent) at 01:30, `expireSubscriptions()` (`server/jobs/expireSubscriptions.js`, built Phase 10 — advances the persisted subscription status through its four transitions and emails affected lender admins; enforcement itself never depends on this job having run, see §7). Since the subscription-billing build it also (a) sends a **pre-expiry reminder** 7 days before the anchor date (`currentPeriodEnd || trialEndsAt`), kind `renewal_upcoming` or `trial_ending`, once per anchor via `subscription.reminderSentFor`, stamped only after a confirmed send, so a period extension re-arms it; (b) writes a `subscription.status_changed` row (`source: 'system'`, `meta.kind`) to `BillingAuditLog` per automatic transition, with no row for reminders; (c) catches errors per lender and returns `errors` and `auditWriteFailures` counts. The job `require`s the audit model itself, since it runs standalone at 02:00, and `sendPaymentReminders()` (`server/jobs/sendPaymentReminders.js`, built Phase 09 — T-3-day reminders and overdue notices, both idempotent via `reminderSentAt`/`overdueNoticeSentAt` stamps on the installment) at 08:00. Manual/operator triggers: `pnpm job:overdue` (`server/jobs/runMarkOverdue.js`), `pnpm job:rollover` (`server/jobs/runRollover.js`), `pnpm job:subscriptions` (`server/jobs/runExpireSubscriptions.js`), and `pnpm job:reminders` (`server/jobs/runSendReminders.js`) — also how the first production backfill/send happens post-deploy. Any job that populates a ref (e.g. `applicant`) via its standalone manual-runner script must explicitly `require()` that model first — the runner scripts don't load `app.js`, so nothing registers the schema otherwise (hit and fixed in Phase 20 for `rolloverLoans.js`/`runRollover.js`; `sendPaymentReminders.js` already had the pattern). Single-process assumption only; if the Coolify migration ever runs more than one server instance, these jobs need a lock to avoid double-running.
